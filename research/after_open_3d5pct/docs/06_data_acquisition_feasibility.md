# 新策略必需数据：采集可行性评估与 coder 交接单

评估日期：2026-09-25，Asia/Shanghai。现场检查主要发生在 01:44–01:49，即美东 2026-09-24 午后。状态：**评估完成；未启动批量采集、未修改下载器、未训练模型。**

本文件可独立交给负责抓数据的 coder。范围是用户最新讨论中的必做数据，以及获取它们所必需的时间、完整性、版本和频率控制。报价盘口、宏观结果、历史分析师一致预期不列入第一批硬依赖。

## 1. 结论与执行顺序

**可以启动价格/成交量原型，也可以补建全时段数据集；当前主要障碍是完整性与时间口径，不是已发现的行情权限不足。** 小规模现场请求已取得未复权 5m、60m、日线及复权因子。但这只证明被测股票/日期可获取，不证明全部股票、所有历史时段都完整。

必须分成三包交付：

| 数据包 | 必做内容 | 可行性结论 | 依赖/限制 |
|---|---|---|---|
| P0：价格模型 A/B | 个股与市场/行业基准的未复权 5m、60m、日线；公司行动；日历；股票池历史；来源与覆盖清单 | 行情技术可行，需先修下载器，再小批验证后扩量 | 历史成员记录尚未具备；5m尚未归档；不能把今天名单当历史池 |
| P1：事件模型 C/D | 财报/指引/订单/产品/展会的原文、发布时间证据、版本、股票映射和覆盖记录 | 财报/披露可系统化；订单、产品、展会为逐公司/逐来源有条件可行 | 没有一个已验证的免费统一接口能保证全部事件及首次公开时刻完整 |
| P2：前向数据记录 | 实时 bar 到达时间、事件首次发现时间、每天股票池版本、重拉修订记录 | 需要做；能补上历史回填无法恢复的真实到达时间 | 历史回填完成不等于具备 11:30:30 全池实时出结果能力 |

四个模型输入版本定义：A=常规时段价格、成交量及市场/行业状态；B=A＋盘前/盘后/夜盘；C=A＋事件；D=A＋延长时段＋事件及交互。采集时保留统一原始资料，让后续实验能分别检验每一类输入的增量价值。

“保留延长交易时段”是原始数据要求；**主入场及 +5% 标签仍按正常时段、1170 个正常交易分钟计算**。凌晨触及不得混入主成功率。B/D 是新增输入版本，实施时升级特征契约，不静默改写原有 v1。可另存“同一标签终点前全时段触及”对照标签，清楚命名。

本评估不把“夜盘代表机构预判”“事件一般带来 2–4 天上涨”设为事实，也不要求抓取所谓机构身份或按上涨结果筛选事件。

## 3. 频率、额度、耗时：分别管理

### 3.1 Futu 历史请求

官方说明：历史 K 线首页请求上限为 **60次/30秒**，连续分页不适用该首页限频；推荐每页1000根，继续传回 `page_req_key` 直至为空。分钟级文档上限为近8年、日线近20年，**扩展时段可能不足2年**，实际逐股探测。ALL 用于24小时行情；不能传仅供交易的 OVERNIGHT。分钟级才支持延长时段，不能要求 K_DAY 返回分时段日线。[Futu 历史K线](https://openapi.futunn.com/futu-api-doc/quote/request-history-kline.html)

历史额度按最近7天不同标的计算，同一标的不同粒度不会重复占额。SDK返回的是 `(used, remaining, details)`，第二项不是总额。本次总额为220+80=300。根文档“近30天60m免额度”未在当前官方说明中得到支持，**不要据此做容量规划**。[权限与额度](https://openapi.futunn.com/futu-api-doc/intro/authority.html)、[额度明细](https://openapi.futunn.com/futu-api-doc/quote/get-history-kl-quota.html)

推荐工程调度值（是保守配置，不是新的供应商承诺）：

- OpenD回填单 worker；首页间隔至少1.2秒，连续页间隔至少0.25秒。考虑其他正在运行的抓取任务，共用一个限流器/任务锁，不按每个脚本各自计算上限。
- 每条请求记录参数、起止时间、返回行数、耗时、错误码、是否有下一页、重试次数；单次超时、重连、失败页都要可恢复。
- 限频：尊重重试提示，至少等待一个30秒窗口，加抖动后有限重试；额度不足/权限拒绝停止对应队列，不能无限重试。网络错误指数退避并设置总重试上限。
- 每批前后读额度明细。新加入的行业ETF、历史退出成分会占用新标的额度；当前名单全部已占用，只是本次快照，不是长期保证。
- `get_rehab`另设队列，先按1.2秒/调用运行，不与历史首页同时抢跑；当前接口实际限频错误优先。复权接口有明确字段和计算关系，现场调用已成功。[复权因子](https://openapi.futunn.com/futu-api-doc/quote/get-rehab.html)

**已占用股票可复用额度，因此剩余80不是“最多只能抓80只5m”。** 同样，页数很多也不等于消耗同样数量的股票额度。

| 数据 | 182交易日估算 | 252交易日年度规划估算 |
|---|---:|---:|
| 5m正常时段，按78根/完整日 | 1,561,560行 | 2,162,160行 |
| 5m全时段，按完整24h最多288根/交易周期 | 5,765,760行 | 7,983,360行 |

上限密度估算不代表每个自然日、周末和假日都应有这些行。月度切块可提高断点恢复能力，但会增加首页和不足1000行的尾页，页数需按实际块重算。

原始数值表按100–200 bytes/行粗估，首轮5m在0.6–1.2GB未压缩数量级；这不是实测Parquet大小。包含源响应、归一化、多个版本和工作空间，先预留5–10GB，再用试采压缩比调整。不要从37.9MB小时库直接承诺5m压缩体积。

首批单日5m请求耗时约2.2–3.1秒，不能直接当满页吞吐。用 `总时间≈Σ响应耗时+首页间隔+续页间隔+重试` 估计；工程排期先按**数小时**安排。先跑5只×1个月，测每1000行耗时、页数、失败率、压缩体积，再报告全池完成时间，不承诺“几分钟抓完”。

### 3.3 数据频率与模型频率不能混为一谈

模型每小时更新，并不意味着源数据只要每小时抓一根。5m用于入场/标签和前两小时路径；60m用于多尺度走势；日线用于完整日背景；事件是异步到达。

**当前30秒出结果假设，与临时串行拉全池历史API不相容。** 110个代码光1.2秒首页间隔就约132秒，还没算响应时间。即便缩小间隔，也不能保证全池在cutoff后30秒到齐。

因此历史回填与前向采集分开：

| 数据 | 回填/刷新建议 | 运行时要求 |
|---|---|---|
| 5m ALL | 初次分块回填；每天补闭合区间，有限重叠重拉并保留修订版本 | 常驻推送采集或提前持续缓存，记录每根bar更新时间；断线后历史接口补洞 |
| 60m/日线 | 完成相应周期后更新；5m聚合已验证时减少重复请求 | 小时尾柱/日线未闭合不能进入完整周期特征 |
| 公司行动 | 初次全量，之后每日检查；发生调整后重建派生版本 | 因子变更不能悄悄重写历史特征快照 |
| 股票池 | 每个交易日保存官方快照；监测增删公告 | 按生效时间和已知时间启用，不按抓取日回填历史 |
| IR/SEC事件 | 初次历史索引和原文；之后增量 | 先按来源支持的RSS/接口；普通时段5–15分钟检查、已知财报窗口1–2分钟为工程建议，并受站点政策约束 |
| 交易日历 | 初始生成全年度并核对；每日检查更改公告 | 正常时段与经纪商夜盘开放表分别版本化 |

Futu实时订阅支持 ALL，但**实时订阅额度、延迟权限、连接稳定性须另行只读核验/试采**，本次历史额度测试不代替它们。优先只订阅所需K_5M，再派生小时特征，避免无意义地同时订阅多种类型占额；本次未新增订阅或启动守护任务。[Futu 订阅接口](https://openapi.futunn.com/futu-api-doc/en/quote/sub.html)

如果全池数据未到齐，应记录迟到并等待/输出不可用。可以后续修改出结果时延假设并重放验证，不能通过伪造 `available_at` 满足30秒约束。

## 4. 数据口径实测：哪些地方必须修正

### 4.1 时间标签与昨收

官方 `last_close` 是上一根K线收盘价；AAPL、NVDA、QQQ抽查与前一根close吻合率100%。**前一正常交易日收盘价必须从正常日历的收盘bar取出**，不能用盘前bar的 `last_close`。[Futu 字段定义](https://openapi.futunn.com/futu-api-doc/en/quote/request-history-kline.html)

AAPL 2026-09-23 的5m/60m现场对账：按 `(09:30,10:30]` 等结束标签区间聚合，7根常规小时/尾柱的OHLC全部一致；前六段各12根5m，最后一段6根。volume每段差2–6股，turnover差约0.001美元，保留差异，不擅自判定原因。这个样例支持 **5m和60m均为结束标签**，生产仍需抽查不同股票、半日、扩展时段边界。

重要边界：5m标签09:30属于开盘前最后一根；09:35才覆盖09:30之后的首5分钟。现有工程要求entry=`bar.start_at`，因此默认11:35入场应使用**源标签11:40的5m Open**。误用标签11:35的Open，会提前到11:30，消除本来要模拟的人工延迟。

每条bar保留 `source_time_key`，规范化另建 `bar_start_utc/bar_end_utc`、`timezone=America/New_York`、`session_type`、`trading_session_date`。不要统一“标签减60分钟”：09:30和16:00附近有半小时柱，半日市还有其他边界。

### 4.2 未复权不自动解决VWAP问题

现有AAPL小时文件中，`turnover/volume` 在正成交量情况下有1,660行超出 `[low−0.01, high+0.01]`；QQQ有2,974行。该筛查只是提示口径不一致，不能据此直接判定价格或成交量错误。

更关键的是：现场取得的 **AAPL 9/23 NONE 5m** 也出现异常：

| 时段（按结束标签归类） | 行数 | volume=0 | 比值超出高低价±$0.01的行数 |
|---|---:|---:|---:|
| 夜盘 | 96 | 2 | 0 |
| 盘前 | 66 | 0 | 26 |
| 常规盘 | 78 | 0 | 0 |
| 盘后 | 48 | 0 | 32 |

QQQ同日NONE 5m也有37行超界；未对它逐时段展开检查。结论是：**不能把所有差异归因于QFQ，更不能承诺切到NONE就得到可信VWAP。** 需要检查成交量单位/取整、各字段成交覆盖、提供方处理和修订；本次没有证据确定根因。

coder必须：保存原始OHLCV及turnover；为比值设置 `vwap_quality`；有明显超界、零分母或混口径时该特征为null并附原因。不要删除原始bar、把比值裁剪到高低价内、或用HLC3冒充真实VWAP。首轮原型可以用已审计的价格/量特征，单独禁用不可信VWAP族。

`pe_ratio=0`、分钟 `turnover_rate=0` 不进入首轮特征。后者官方仅提供日K及以上口径；保留原值和支持状态，不能当作公司“零换手”或“零估值”。[Futu 历史K线限制](https://openapi.futunn.com/futu-api-doc/quote/request-history-kline.html)

### 4.3 公司行动

归档 `get_rehab` 全部返回行、除权除息日期、拆合股/现金分红/分拆字段、调整因子、抓取时间和哈希。因子当前版本不是当时已经知道的公告；若作为特征，还需当时公开证据。

标签需要一致的入场单位：例如持有期间1拆2，目标价格应随持股单位调整；不能用未复权序列直接算出−50%，也不能把整个窗口后来前复权后仍称原始现金价格。现金分红是否进入收益属于另一目标；当前+5%价格触及不自动改成含息总回报。保留原始数据，派生调整算法单独版本化并做公司行动样例测试。

## 5. 延长时段：必须保留，但完整性不能只靠补齐网格

正常盘日历按Nasdaq开收盘、假日和半日市处理；夜盘还依赖经纪商/交易场所的开放与股票资格。Moomoo的24小时安排为周日20:00至周五20:00 ET，且不是全部股票都必然支持；假日另查。不能依据常规盘日历凭空创建每晚20:00–04:00的数据。[Moomoo 24小时交易说明](https://www.moomoo.com/us/support/topic4_664)

以周一11:30决策为例：分别取上一个常规收盘后的盘后、实际开放的周日夜盘、周一盘前和周一前两小时；保留各段与当前时刻间隔。不要制造周五夜盘、把周日记录丢掉，或把相隔几天的时段无缝连接成一晚。

归档自然时间；特征层再按实际session映射到决策日。对午夜标签补取请求日期边界外的数据，例如目标日起点之前的有效上一晚，避免日期过滤裁掉跨午夜窗口。夜盘量与历史同类夜盘比较，并保留绝对成交额、有效交易bar数量、无成交持续时间。

每个 `symbol × session × granularity` 至少有以下覆盖状态：

| 状态 | 判定要求 | 不允许的替代做法 |
|---|---|---|
| observed_trade | 有效bar且成交量>0 | 仅有非空价格就当作活跃成交 |
| zero_volume_reported | 提供方明确返回volume=0的bar | 把所有缺条补成这种状态 |
| confirmed_no_trade | 另有提供方证据说明开放但无成交 | 无证据就断言该股票没有交易 |
| market_closed / not_supported | 有日历或股票时段资格证据 | 与抓取失败共用一个null |
| halted | 有停牌证据及时间范围 | 把停牌当休市或涨跌失败 |
| missing_unknown / fetch_failed | 预期开放但信息不足/请求失败 | 通过前向填充变成可成交价格 |
| not_yet_closed / revised | 当前bar未闭合/后续被修订 | 用最终修订版假装当时已经可见 |

主标签窗口若缺必要价格，必须标记不可判定；即使此前已触及，也不能只保留这个正例而丢掉同类未触及样本。扩展时段缺失只影响对应B/D输入质量，不应自动删去A模型可用样本。

## 7. 事件数据：可行范围、采集频率与时间精度

### 7.1 各类事件的可行性

| 事件 | 第一来源/获取办法 | 可行性 | 必须保留的限制 |
|---|---|---|---|
| 财报与指引 | 公司IR新闻稿＋SEC 8-K/6-K及附件；10-Q/10-K用于补内容 | 高，适合第一批系统化 | SEC文件可能晚于新闻稿；文件接受时间不一定是事件首次公开时间 |
| 大订单/合作 | 公司及交易对方新闻室、对应8-K/6-K附件 | 中 | 并非每笔订单都公告；没有抓到不等于没有事件 |
| 产品发布 | 官方新闻室、产品发布文章/发布会材料 | 中 | 新闻稿、发布会、上市日期分别记；后续编辑不能覆盖初版 |
| 展会/演讲 | 主办方议程、公司参会公告、演讲材料及现场正式发布 | 中至低，需维护每个来源 | 日程不等于新信息；网页只写日期时无法恢复分钟级首次公开时间 |

NVIDIA官方活动页可作为来源目录之一，本次页面可读，但没有据此核验全部历史原文和发布时间。不能将“有活动页面”当作已有完整事件库。[NVIDIA 活动入口](https://investor.nvidia.com/events-and-presentations/events-and-presentations/default.aspx)

事件模型的必做项是**原文与时间证据管线、来源覆盖台账、事件去重和缺失标识**。首批先覆盖全部入选公司的财报/指引，再逐来源纳入其他类型；未完成的类型明确为未覆盖，不能把C/D解释成包含所有事件。

### 7.2 SEC接口与频率

SEC Submissions API无需API key，支持按CIK索引提交记录，并指向更早历史JSON；不能只读 recent 节点便认定全历史齐全。抓正文及附件时记录 accession、原始文件与版本；Company Facts提供财务事实，不能替代公告原文，也不提供发布前一致预期。[SEC API](https://www.sec.gov/search-filings/edgar-application-programming-interfaces)

SEC最大访问率为10请求/秒，要求声明含身份及联系地址的User-Agent。工程按全局2请求/秒起步，跨任务合并限流、缓存、有限退避。本次环境 `SEC_USER_AGENT` 未设置，所以没有进行SEC批量API探测；由coder配置真实有效联系信息，不能编造。[SEC 开发访问规则](https://www.sec.gov/about/webmaster-frequently-asked-questions)

对101个候选，应按唯一CIK去重（多股类可共享公司），先请求索引，再按日期和表单选正文/附件；请求数量是“CIK索引＋历史索引＋原文＋附件”，不是101次就能完成。历史量大时再评估SEC官方bulk archive，不必为了小池默认下载全站。

IR/新闻室/主办方没有统一限额。每个域名单worker，初始请求间隔2–5秒，尊重站点规则、Retry-After和缓存；不可直接套SEC的10请求/秒。首次获取目录和来源证据后再确定增量频率，失败留日志。

### 7.3 时间与版本契约

每条事件至少保存：

```text
event_id / event_cluster_id / parent_event_id
security_id / symbol / event_type / source_role
event_at                       # 实际发生/预定举行时间，不能代替公开时间
first_public_at                # 有证据的首次公开时刻；允许null
public_time_precision          # second / minute / date / unknown
public_time_evidence_url
source_available_at            # 来源公开可取得时间；可能为估计
first_seen_at                  # 本系统实际首次看到，历史回填时就是今天
fetched_at / raw_url / content_sha256 / raw_file_path
revision_id / supersedes_id / extraction_version
availability_quality           # observed / historical_verified / assumed / unknown
coverage_status / dedup_reason
```

必须区分“来源当年公开”与“系统今天补抓”：不要把 `first_seen_at` 回填成公告日期。历史回放只有在当年原文版本和发布时间有证据时，才能使用单独的历史可用性估计并标记质量；前向运行采用实际到达时间。SEC接受时间也不等于页面首次可用时刻，官方FAQ明确没有直接提供后者的时间戳。[SEC 时间说明](https://www.sec.gov/about/webmaster-frequently-asked-questions)

仅有发布日期、没有具体时刻的事件，默认不进入当日盘中事件特征；不能补成00:00。只有确认当年内容版本和日期后，才可按登记的保守规则从后续决策时点使用，否则保持不可用。公告变更、指引更新是新版本；转载去重到原始事件，新实质进展另建关联事件。

财报“超预期”需要发布前已存在的一致预期快照；本轮未确认这类源，不生成该特征。业绩日程的“下一事件距离”也要保留当时已知的日程版本，不能用今天已修订的日期倒填。

无事件对照必须来自**同一时期且来源已成功覆盖**的股票日；采集失败/来源未覆盖标unknown，不能自动标无事件。采集所有符合类型的事件，不按公告后上涨、热搜或模型信号筛选。

### 第三步：验收门槛

- 原始记录100%能追溯到请求/快照；主键重复或混价格基准不得静默通过。

- 可以保留不完整数据集，但每个缺口必须有状态。**只有输入前缀与标签窗口均满足契约的样本才有资格训练**；完整样本数和排除分母同时报告。
- AAPL式5m→60m OHLC对账扩展到多股票、多日期；volume/turnover差异记录绝对与相对偏差，先解释单位与舍入，不能事后调容差掩盖问题。
- NONE也需做VWAP一致性筛查。异常不阻止原始数据归档，但阻止相关VWAP特征启用。
- 没有PIT成员证据，交付标探索池；没有精确事件时间/历史版本，标对应特征不可用；没有夜盘资格证据，缺条不得标无成交。

- A/B/C/D保留各自全部可用样本计数；模型消融比较用预登记的相同日期与可比样本，另报覆盖差异。不能为了B/C/D完整，悄悄只留热点/有事件/容易抓到的股票。

交付结论分别标注：**接口可调用、数据已归档、完整性已通过、历史可回放、前向时延已验证**。这五项不是同一个“抓取成功”。此后的模型训练与样本外预测能力不属于本次采集验收。
